# Gate, build and startup

The named check/build owner runs these on a stable source snapshot, one heavy command at a time, using the project's full-app scripts. For an independently ready journey, use an early snapshot when the full-app check, build and startup can run on stable inputs without blocking other critical-path work. Coordinate the full set of check and build inputs: use an already supported isolated snapshot, or a short coordinated freeze only if neither blocks critical-path work. Keep the served app unchanged during its browser item, and let remaining work continue without affecting that snapshot. Do not wait for unrelated owners just to group verification; if those inputs cannot remain stable without disrupting critical work, use the integrated batch. No check or build inputs change while their command runs. Track the build identity and unbuilt work; do not treat a partial snapshot as proof of later changes.

1. Run the project-wide lint/type check for the stable snapshot; it is not file-scoped, and the project's test suite is not part of it (tests follow `testing.md`). Report failures to main, which routes each to the responsible owner or explicitly hands you the fix. An unrelated error does not make another owner's work incomplete or require that owner to redo it or rerun its direct check. Before completion, establish a passing full-app check on the final snapshot of all inputs that check covers, including non-runtime inputs changed after an earlier check. Reuse a previous passing result only when those inputs are unchanged. After corrections, rerun the full gate when necessary; never treat a failing full gate as a pass.
2. Build the full app once from stable, passing inputs. Rerun a failed build or rebuild after changed runtime inputs as needed, not once per owner.
3. Apply required authorized application migrations through the repository-owned migration path after testing on isolated disposable storage. Start the app using the project-supported command and task-supplied address, with existing access or access prepared by main or an assigned worker, and confirm startup and required access without printing secrets. Record the owned PID in `task-workflow/app.pid` and log in `task-workflow/app.log`. Never replace or stop the platform preview or reset or seed live or shared data. Main or an assigned worker may set up sign-in for an existing or new user in the confirmed isolated app database copy, following the common app-database guidance; never alter the live account or unrelated data. The worker returns needed access privately to main, which passes it to the browser-only app driver.
4. Report each command's own exit code, never one read through a pipe (`| tail`), the startup result, the served build identity and that the app is running.

Rebuild only for changed runtime inputs or a failed build, and repeat the startup check after each rebuild. Test-only edits outside served inputs never rebuild; judge by actual runtime/build dependencies, not file names. Rebuilds happen only between app driver items: before overwriting served assets, confirm no app driver is running, then stop the app from `task-workflow/app.pid`, and only that process, and start the new build the same way. Never run a competing app. Reuse results; rerun only for changed inputs or a concrete failure. A build request is not a new audit: report known missing outcomes.
