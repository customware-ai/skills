# Gate, build and startup

The named owner runs full-app scripts on a stable source snapshot, one heavy command at a time. For early verification of an independently ready journey, coordinate all check/build inputs using an already supported isolated snapshot or short freeze only if neither blocks critical-path work; otherwise use the integrated batch. Don't wait for unrelated owners merely to group verification. Keep served artifacts unchanged during the browser item while other work continues without affecting the snapshot. **Critical:** Never change check/build inputs while their command runs. Track build identity and unbuilt work; a partial snapshot cannot prove later changes.

1. Run the project-wide lint/type check, not file-scoped; tests are separate (`testing.md`). Report failures to main to route or explicitly assign you to fix. Unrelated errors do not invalidate another owner's work or require its direct check again. Before completion, require a passing full-app check on the final snapshot of all covered inputs, including later non-runtime changes; reuse a pass only if those inputs are unchanged. **Critical:** Never treat a failing gate as a pass.
2. Build the full app once from stable passing inputs, not per file or owner.
3. Test required authorized migrations on isolated disposable storage, then apply via the repository-owned path. Start with the project-supported command, task-supplied address and existing or prepared access; confirm startup and access without printing secrets. Record the owned server PID in `task-workflow/app.pid` and log in `task-workflow/app.log`, both at the repository root. With `build && node ... &`, `$!` may identify the shell, not the server. Never replace or stop the platform preview or reset or seed live or shared data. Main or an assigned worker may set up sign-in for an existing or new user in the confirmed isolated app database copy under common app-database guidance; never alter live accounts or unrelated data. Return needed access privately to main, which passes it to the browser-only app driver.
4. Report each command's own exit code, never one read through a pipe (`| tail`), startup result, served build identity and that the app is running.

**Critical:** Rebuild only for changed runtime/build inputs or a failed build, and only between app-driver items; test-only edits outside served inputs never rebuild. Judge actual dependencies, not file names. Before replacing served assets, confirm the driver is idle; stop only the PID in `task-workflow/app.pid`, restart identically and recheck startup. Never run a competing app. Reuse results; rerun only for changed inputs or concrete failure. A build request is not a new audit: report known missing outcomes.

**Critical final step:** Before returning, update only your own rows in the repository root's `task-workflow/checkpoint.md` with an exact-text edit, never rewriting the file: outcome, implementation state, and each proof's **unverified, passed, failed or blocked** result with a concise evidence reference and build or blocker when applicable; also record app-driver results included in your assignment. Change only facts that changed. Checkpoint rows are your only exception to file ownership; create no other tracking documents.
