# Implementation rules

- **Required inputs.** Require every new behavior-changing input at each call site; never default it to an empty value (`[]`, `null`, `{}`). Unwired callers must fail type checking, not assume no data.
- **One transition, one implementation.** Preview and save of the same rule or state change share one function; reject inputs irrelevant to the chosen operation rather than ignoring them.
- **Prove the assembled path.** A correct helper alone does not prove the live caller fetches and passes inputs. Self-check the real caller chain; every live-path call site receives new inputs. Report callers missing from main's trace.
- **Critical: least proof.** Test only the changed path, never the whole app; start minimal. Normally start with a happy path and a wrong path (a wrong input, to show the error is handled); add every distinct required or warranted case main names, without a cap.
- **Required product patterns.** Settle contracts and outlines to the repo `AGENTS.md` required product patterns before dispatching workers: cursor-paged lists, optimistic predictable changes, `Button` + `Spinner` pending submits, invalidation of exactly the changed queries. Never trade them for speed.
- **Least code.** Reuse existing code, remove superseded paths, and add no speculative options, abstractions, cleanup or polish.
- **Account access.** Separately from direct-check scripts, when assigned by main, update an existing user's sign-in or create a user in the confirmed isolated app database copy under common app-database guidance. Never alter the live account or unrelated data; report access privately to main.
- **Proof and checks.** Prove an assigned shared boundary as soon as usable, notify main with evidence via `notify_parent`, then continue independent work; do not prove the whole unfinished assignment yet. Before final handoff, finish every edit and caller of a changed type, signature or input; find callers with `rg`, not the full-app check.
  1. Only if assigned script cases, write one direct-check script for the assembled path (the live caller with real inputs). Example: add ‘Read’; reject an empty name without adding a row. Assert expected results, including returned values and saved-state reads or counts when needed. Run against a repository-owned isolated disposable target, shared only when safe; tell main if unusable. If adding or renaming a router, procedure, route or exported name loaded at startup, load the real root router or route table and call the procedure through it, not just the service module. Never assume empty tables. Create and assert your own marked records; delete only those at script end. Existing records are read-only: never delete, truncate, drop or replace anything you did not create.
  2. If it fails, fix everything shown in one pass and rerun the same script once. A still-failing case goes to main with output; never add your own cases, write more script or loop.
  3. The named check/build owner runs the project-wide check and full build for the integrated batch; no per-file check. Route errors to the affected behavior's owner. Unrelated failures do not invalidate completed work or require its direct check again. If a correction changes a boundary or dependencies, rerun affected proof; rerun the full gate as needed on corrected integrated inputs. **Critical:** Never claim a failing gate passes.
- **Critical final step:** Before returning, update only your own rows in `task-workflow/checkpoint.md` with an exact-text edit, never rewriting the file: outcome, implementation state, and each proof's **unverified, passed, failed or blocked** result with a concise evidence reference and build or blocker when applicable; also record app-driver results included in your assignment. Change only facts that changed. Checkpoint rows are your only exception to file ownership; create no other tracking documents.
