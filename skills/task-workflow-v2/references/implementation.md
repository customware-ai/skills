# Implementation rules

- **Required inputs.** A new input that changes behavior is a required parameter at every call site. Never default it to an empty value (`[]`, `null`, `{}`); an unwired caller must fail type checking instead of silently acting as if there were no data.
- **One transition, one implementation.** When the same rule or state change is previewed in one place and saved in another, both use one shared function, and inputs irrelevant to the chosen operation are rejected, not ignored.
- **Prove the assembled path.** A helper that is correct when given its inputs proves nothing about whether the live caller fetches and passes them. Self-checks exercise the real caller chain, and every call site on the live path must receive the new inputs. Report any caller missing from main's trace.
- **Least proof.** Start minimal and add only what the change needs: test only the changed path, never the whole app.
- **Least code.** Reuse existing code, remove superseded paths, and add no speculative options, abstractions, cleanup or polish.
- **Account access.** This is separate from a direct-check script: when assigned by main, a worker may update an existing user's sign-in details or create a user in the confirmed isolated app database copy, following the common app-database guidance. Never alter the live account or unrelated data; report the necessary access privately to main.
- **Proof and checks.** Implement and prove an explicitly assigned shared boundary as soon as it is usable; send its readiness notice with evidence through `notify_parent`, then continue remaining independent work. Prove only that boundary at this point, not the whole unfinished assignment. Before the final handoff, finish every edit and every caller of a changed type, signature or input: find callers with `rg`, never by treating the full-app check as a search tool.
  1. Only if your assignment names script cases, write one direct-check script for the assembled path (the live caller with real inputs) with normally two cases: one happy path and one wrong path (a wrong input, to show the error is handled). Add every case main names for distinct task-required or warranted behavior; the happy and wrong paths are a starting point, not a cap. Assert the actual expected result for each case, including relevant returned values and saved-state reads or counts when needed. Run it against a repository-owned isolated disposable target, shared only when safe; tell main if it becomes unusable. When a change adds or renames a router, procedure, route or exported name the app loads at startup, the script loads the real root router or route table and calls your procedure through it, not only the service module. Never assume a table is empty. Create and assert on your own marked test records, delete only those when the script ends, and read existing records without changing them. Never delete, truncate, drop or replace anything you did not create.
  2. If you ran it and it failed, fix everything it shows in one pass, then rerun that same script once. A case still failing goes back to main with the output; never write more script, add cases of your own or loop on it.
  3. The named check/build owner runs the project-wide check command and full build for the integrated batch; there is no per-file check. Route errors to the owner of the affected behavior. A failure in unrelated work does not invalidate your completed work or require rerunning your direct check. If your correction changes a boundary or its dependencies, rerun the affected proof; the full-app gate is rerun as needed on corrected integrated inputs, never claimed to pass while failing.
