# Task workflow

This skill is the orchestrator's. Read `AGENTS.md` at session start and again after compaction, and follow it. Deliver the whole approved task with the least product code. The orchestrator role says what main decides; this skill sets the delivery order, test decisions, retests and the checkpoint. Workers read only the reference their assignment needs, so name it in every assignment:

- [implementation.md](references/implementation.md): foundation and feature owners. Main designs outlines to these rules.
- [build.md](references/build.md): the check/build owner (gate, build, startup check).
- [testing.md](references/testing.md): test owners (test scope, E2E isolation commands).

## Checkpoint

Main assigns a worker to maintain one file, `task-workflow/checkpoint.md`, holding only:

- each required outcome, its implementation state and the proof types it needs: for each required direct check or browser proof record **unverified, passed, failed or blocked**, with a concise evidence reference, relevant build and blocker when applicable. A case needing both proofs is complete only when both pass; a proof not required is not an outstanding case;
- the task identity, settled contracts and live path of each changed journey;
- owners and their exclusive files;
- the focused verification items, the outcomes they cover and their current results.

Main directs its worker to change a line only when that fact changes. Keep concise results and references, not narrative, logs or evidence copies. After compaction, reread the task and domain inputs, reconcile the checkpoint with Git status and diff, then load only unfinished work. Never replace another task’s snapshot without confirming its identity. Create no other tracking documents; command logs and evidence files the work already produces are fine.

## Delivery order

0. **Research and plan in parallel.** Main reads the core, settles names and dispatches explorers and any ready owners. Map each shared boundary, its consumers and its readiness checks; prepare verification journeys and valid real inputs from owner handoffs as they arrive while implementation continues. Prepare the full-app gate assignment before the source snapshot is ready.
1. **Foundation, only if needed.** One worker owns only common schemas, migrations, shared contracts and database queries. Reuse existing contracts. Apply and check each migration on isolated disposable storage before a consumer needs it. A boundary proven by the assigned relevant check can unblock its consumers before the foundation's other work is finished. A type can unblock a type-only consumer, but types or stubs alone never prove a working runtime boundary. The full-app check is not required for each boundary.
2. **Feature owners** start as soon as their own dependencies are usable, not when all foundation work returns. A continuing owner signals a checked shared boundary once to unblock main and other owners; main immediately launches ready consumers, while the first owner finishes its remaining work. Preserve exclusive files and implement each feature end to end under `implementation.md`.
3. **Full-app check, build and startup** by the named owner under `build.md`, as soon as the required served source snapshot is stable, not automatically per partial return. Do not delay this handoff for a separate verification-planning or audit phase. For an independently ready journey, coordinate a stable snapshot of every input read by the full-app check and build: use an already supported isolated snapshot, or a short coordinated freeze only if neither blocks critical-path work. Start its browser item early only after that snapshot passes check, build and startup; keep the served artifacts unchanged during the item. If those inputs cannot be kept stable without disrupting critical work, use the integrated batch; do not wait for unrelated owners merely to group verification. Unfinished approved work may continue without changing the served snapshot during an item. Never modify build inputs while the check or build is running, and never rebuild the served app while an app-driver item is running. Later runtime changes need the full-app gate/build handoff before their own proof; earlier results remain valid only where those changes cannot affect them. There is one repository-wide check command and one full build command, not per-file checks or builds. Prepare verification and complete independent direct checks in parallel; do not run the shared full gate separately for each owner. Route failures to the responsible owner. Unrelated owners retain completed work and direct-check evidence. Before completion, require a passing full-app check on the final snapshot of every input covered by that check, including non-runtime inputs changed after an early check. Reuse the result if those inputs are unchanged. Build the full app again only if build/runtime inputs changed or a build failed; never accept a failing gate as passed.
4. **Verify.** Plan while work runs; execute only after the startup check passes on the built app. Give the app driver **one focused item at a time**, in a fresh session; dispatch the next only after the previous returns. Never give it the whole list or story. Main maintains the minimum focused items needed for complete coverage in the checkpoint, choosing the highest-risk ready item whose dependencies are met; items follow the task's Reviewer requirements, one per screen or control journey they name. Prepare each item’s route, actual starting state, valid setup, necessary supported controls and required outcomes from owner rows while implementation continues. Check whether the record or choice already exists before selecting add versus update; preserve expected unchanged or blocked outcomes. Start the first ready item as soon as startup passes; dispatch the next after the prior return without unrelated replanning. Reuse reported identities and shared browser state when valid. Each item gives the minimum user journey and required outcome, not an observation after every action; retain every task-required visible proof and save/reload check.
5. **Tests**, when warranted, start at the same time as verification in a separate test worker under `testing.md`; neither waits for the other, and no additional application build is needed. A failure found there joins that round's corrections.

Rebuild only for changed runtime inputs or a failed build; a passed or intended item changes nothing, so no rebuild, app restart or new build-owner handoff is needed; send the next focused item straight to the running app. Group known corrections into one rebuild when safe. The app driver is idle between items, so rebuild only between items, never while one runs; the build owner stops and restarts the app (PID file) around a rebuild, never the app driver. Test-only changes never trigger a rebuild. Keep the database and records across correction builds; follow the orchestrator’s database and retest rule.

## Test decisions

Start minimal and add only what the change needs: test only the changed path and what it touches, never the whole app. This holds for app driver items, owner script cases and other tests alike; an existing suite for the whole app is not rerun or extended.

Main routes each case. Keep every task-required on-screen observation and screen-wiring check as a browser case, never dropped. For remaining required behavior (saved values, order, approvals, exclusions, quantities and reversal), assign the appropriate direct checks under `implementation.md`; start with a happy path and a wrong path, then name every additional distinct case needed to prove the task or warranted coverage, without an arbitrary cap. A script case that still fails after one rerun returns to main, who fixes the product or drops only a non-required case; never nudge an owner to keep looping. Give the app driver one focused item at a time, choosing the highest-risk ready journey whose prerequisites are met, including the central journey when ready; add any item needed for required observations not yet covered. Decide automated tests under the project's rules, including core behavior, complex flows, stable contracts and regressions; reuse existing targeted coverage first. Start with a happy path and a wrong path where applicable, adding all cases needed for the required coverage. When a transition is both previewed and saved, a warranted case calls the real preview and save entry points with the same starting state and inputs, then compares the preview with the reloaded saved values, across its operation shapes. When the change touches the AGENTS record-loading/creation contracts, reuse their existing regression coverage and include saved-value/record-count checks after refresh or retry in the verification cases. A passing test never overrules a failing browser result; the contradiction stays open until the first divergent boundary is found.

## Corrections and retests

1. The app driver (browser harness tools only) reports the failure with build, route, records, steps, expected and observed results. Before a retry, main checks the reported state, inputs and intended operation and establishes the served build and page state; identify a changed condition or a targeted unresolved diagnostic question. Never repeat unchanged work merely hoping for success, replay an acknowledged write, or ask the driver for unsupported DevTools, JavaScript, shell, filesystem or cache controls.
2. Main diagnoses it and gives the owner a fix outline (orchestrator role).
3. The owner fixes it; changed runtime inputs go through `build.md` again.
4. The retest is the next single item on the fixed build (observe-only or fresh write), run in a fresh app driver session, covering only the steps and items the changed code can affect, as main judges from the owner's list of changed files and behaviors; unaffected passed items and unrelated owners' direct checks are not rerun; determine impact by actual changed behavior and dependencies, not file ownership alone. Mark affected evidence as needing retest until it passes on the corrected build.

Keep passed evidence, failed attempts and acknowledged records; never replay acknowledged writes. Verification of unaffected served journeys continues meanwhile. An unbuilt fix is unverified.

## Messages and completion

- A child returns once through native delivery when done or blocked; a continuing owner sends one readiness notice through `notify_parent` when a checked shared boundary unblocks another owner, or for other new information main must act on. No polling, sleeps, progress files or duplicate notices.
- Keep messages short: changed facts, actual results, file paths. Never repeat the task, plan, logs or source.
- If a child fails, recover its unfinished work from the checkpoint and existing state, without replaying successful work. Do not cycle agents or change providers for a deterministic provider or account denial; report it.
- Finish only when the approved outcomes, required checks and corrections are settled, or report exactly what is incomplete or blocked. No extra export or report phase. Runtime helpers, models, providers, allocation and timing policy stay unchanged.
